# Changelog

All notable changes to `@elephantseed/auto-bumper`.

## [Unreleased]

### Fixed
- `fix --apply` (Maven) no longer rolls back downgrades on an environmental compile-check failure: when the pom's required Java release (compiler plugin `<release>`, else `maven.compiler.release`, else `java.version`) is newer than the JDK in `JAVA_HOME`/PATH, the post-downgrade compile check cannot succeed for reasons unrelated to the downgrade — e.g. a pom targeting Java 25 built with JDK 21 fails with "release version 25 not supported". The check is now skipped for that project, the downgrades are kept, and they are reported as `Unverified downgrades` (counted toward a non-zero exit under strict mode) with advice to re-run under the project's JDK
- Compile-check failure details no longer show only the last three lines of build output — for Maven that was always the generic `[Help 1]` footer, hiding the real error. The reported detail now leads with the `Failed to execute goal` / `FAILURE:` headline and its concrete error lines, with the footer noise dropped

## [1.0.0] - 2026-11-12

### Added
- `fix` (Gradle projects on Spring Boot's `io.spring.dependency-management` plugin): vulnerability pins are now written as `dependencyManagement { dependencies { dependency 'g:a:v' } }` entries in the managed block — the only mechanism that beats the component-metadata rule, which outranks both managed constraints and `resolutionStrategy.force`, so force/constraint pins were silently ignored on Spring projects (the classpath stayed at the vulnerable version). With the plugin present, every non-direct planned bump becomes a DM pin; existing DM pins are merged on re-runs (higher wins) and advisory comments are preserved
- Snyk Open Source public advisories as a supplemental advisory source for Maven and npm: the public per-package advisory page of every unique scanned package is fetched once and cached under `.auto-bumper/db/osv/snyk/` with a 7-day TTL (a package absent from Snyk's database is cached as empty). Advisories are converted to OSV format — id is the first CVE alias when present, otherwise the SNYK id; the same CVE keeps every affected package; severity uses the page's numeric CVSS score when present, otherwise critical/high/medium/low map to 9.0/7.5/4.0/3.0, and a missing label maps to 3.0 — so existing matching and fix planning work unchanged. A failed fetch serves the stale cache when one exists (logged); with no cache at all a single aggregated warning is emitted, those packages go unmatched, and the scan is marked incomplete so `fix` will not report a clean result. `--offline` reads the caches without fetching; never-fetched packages produce a "cache missing" warning
- `AUTO_BUMPER_SUPPLEMENTAL` environment variable: setting it to `off`, `0`, or `false` (case-insensitive) disables all supplemental advisory sources — GitHub's reviewed Maven advisory list, the orphan-CVE bridge, and Snyk's per-package advisories — so scans run strictly on the OSV bulk dump plus locally-vendored advisories. Unset or any other value keeps current behavior
- `fix --force-exclude=group:artifact` (Maven/Gradle, repeatable): explicitly approve excluding an unfixable coordinate that other resolved packages still depend on — see the refusal behavior under Fixed
- Vendored two SNYK-only Maven advisories absent from the OSV bulk dump: CVE-2026-93879 / SNYK-JAVA-ORGHIBERNATEVALIDATOR-20877468 (`org.hibernate.validator:hibernate-validator`, fixed 9.2.0.Beta1) and SNYK-JAVA-JAKARTAVALIDATION-20936881 (`jakarta.validation:jakarta.validation-api` 2.0.1–< 4.0.0-M1, fixed 4.0.0-M1)
- `fix --allow-downgrades` (Maven/Gradle): for vulnerabilities with no fixed version in OSV, the tool now computes the newest published **GA** release strictly below the advisory's introduced bound and proposes a downgrade out of the affected window — pre-releases (SNAPSHOT, milestones, RCs, alpha/beta) and Java build qualifiers (`-bNN`) are never targets. Without the flag the proposal is shown in the Unfixable section only; with it, the downgrade is applied (marked ↓ in the plan), a downgrade crossing a major boundary additionally requires `--allow-major` (prompted in TTY), each touched project is compile-checked afterwards (`gradlew compileJava compileTestJava` / `mvn -DskipTests test-compile`) — with an explicit warning that runtime behavior stays unverified — and a failed build rolls back that project's downgrade bumps one by one: original versions kept, reported as remaining issues. Requires an introduced bound on every finding for the package; skipped when `--offline`
- `fix` (Gradle projects on a platform BOM — Quarkus, Spring Boot, or the dependency-management plugin): managed-block pins at or below the version the platform BOM manages are dropped as stale, since they only force an older version than the platform already provides. The BOM's `<dependencyManagement>` map is fetched from the project's declared repositories (Maven Central as fallback) and cached per BOM version under `.auto-bumper/db/bom/` with no TTL; a failed fetch leaves the run without cleanup. New bump targets at or below a BOM-managed version are skipped with a warning instead of writing a pin that would force a downgrade — explicit downgrades (`--allow-downgrades`) are unaffected. Cleanup runs on every `fix` pass, including clean exits where nothing is bumped, and is idempotent
- Health warning for relocated Maven artifact families resolving at different major versions (`Mixed-major relocated family 'X': g1:X@v1 vs g2:X@v2`) — surfaces stacks where an old coordinate and its relocation coexist at incompatible majors (e.g. `org.glassfish.jaxb:jaxb-core` 3.x alongside `com.sun.xml.bind:jaxb-core` 4.x). Families are a small table (`RELOCATED_FAMILIES`) extended as relocations appear
- Co-versioned family guard in `buildFixPlan` (Maven/Gradle): with the resolved classpath known, a cross-major bump target that would split a co-versioned family (`jetty`, `netty`, `vertx`, `jackson`) is clamped to the best same-line GA fix when one exists, and reported unfixable with an explicit reason otherwise — instead of silently desynchronizing siblings that stay on the old line (e.g. pinning `org.eclipse.jetty:jetty-http` 12.x while `jetty-server` / `http2-common` remain on 11.x). Cross-major moves are still allowed when every family member on the classpath moves together, and behavior is unchanged when no classpath is supplied
- Consumer variant swap during family migration (Maven): when a co-versioned family migrates across an ecosystem line (Jetty 11 → 12), consumer artifacts that only publish builds for a specific line are swapped in place to their matching variant — `org.wiremock:wiremock` → `org.wiremock:wiremock-jetty12`, same version line — when they are direct dependencies of the project. Without this, stripping the old transitive coordinates leaves the consumer without an implementation layer (WireMock's Jetty 11 server on a Jetty 12 classpath fails at test time with `HttpServerFactoryLoader` finding no factory). Variants come from a small table (`CONSUMER_VARIANTS`) extended as needed

### Changed
- `fix` (Gradle/Maven): managed blocks written by earlier tool names (`// auto-depender:begin`, and in the oldest files `// depender:begin`) are now recognized as aliases for the current brand. A file holding several managed blocks is consolidated to a single canonical block on the next rewrite — pins, forces, DM entries, and comments merge across blocks (the current brand's block wins version conflicts), and legacy markers never leak out as stray comments
- Reviewed Maven advisories now come from GitHub's global advisory list (`GET /advisories?ecosystem=maven`) instead of a five-repo watchlist. The first pull caches the set; later pulls ask only for rows updated since `repo-advisories.since`. The request does not include the project's package names. A failed fetch keeps the previous cache and does not move the cursor. The now-dead `getWatchedRepos` / `DEFAULT_WATCHED_REPOS` exports are removed
- Maven/Gradle dependency tree parsing now retains parent edges (`PackageRef.requiredBy`: the coordinates that require each package on the resolved classpath), so `fix` can tell whether an unfixable coordinate is still needed by something else before excluding it
- `fix --apply`'s `Applied:` lines report the version actually written to the manifest: when a pin is aligned to a higher declared version elsewhere in the project, that aligned version is reported instead of the requested target
- Maven version selection no longer treats Java build qualifiers (`-b02`, `-b140310.1920`) as release candidates: they are pre-release builds and are now excluded from all target selection — latest bumps, next-after-last-affected promotion, and downgrade targets
- OSV-provided fixed versions that are pre-releases (e.g. `fixed: 9.2.0.Beta1`) are no longer applied as bump targets — such packages are reported under Unfixable naming the pre-release (`no GA fix available; only pre-release X fixes this`), so a production project is never moved to a Beta/Milestone/RC "fix" without an explicit human decision
- `fix` (Gradle): managed-block pins shadowed by the project's own `resolutionStrategy.force` are now removed when — and only when — the user-forced version is not affected by any advisory. The explicit user decision then wins over the tool's pin, which would otherwise silently split a co-versioned family. When the forced version is itself affected, the escape pin survives (last `resolutionStrategy.force` wins in Gradle, and the managed block sits after the project's forces) — dropping it would reintroduce the vulnerability. The warning names the package, the dropped version, and the version the user's force governs; cleanup-only runs (no bumps) apply the same rule

### Fixed
- Matching no longer lets a range with no fix boundary re-flag a version that a sibling range for the same package already closed. A Snyk or mirror record of "introduced, no fixed" is dropped when it starts inside a closed window. A range that starts after every sibling fix is kept, so a newer open line is still reported. The scan table now shows that window (`introduced → fixed`, or `→ last` when nothing is fixed) next to the installed version
- `fix` (Gradle): an undeclared `org.springframework.boot` fix rewrites the Spring Boot plugin version (`id 'org.springframework.boot' version '…'`, Kotlin `id("…")`, or `${springBootVersion}`) instead of pinning one starter. A same-line or cross-minor starter fix on `spring-boot-dependencies` moves that BOM and, when it still matches, the plugin version. Tomcat, Jackson, and other non-Boot artifacts stay on the pin path. A Boot-only build still does not get a `dependencyManagement` block — Boot 3.5 does not apply that plugin, and the block would fail configuration
- `fix` (Gradle, Quarkus): a patch on the same minor line (for example `3.28.5` → `3.28.6`) now bumps `quarkusPlatformVersion` and `quarkusPluginVersion` when they match, instead of force-pinning the one extension off the BOM. Cross-minor platform bumps are unchanged
- `fix --apply` (Gradle): the in-place direct-declaration rewrite no longer matches inside the auto-bumper managed block — a bump of an already-pinned transitive rewrote its constraint/force/DM lines in place and was reported as "(direct)" instead of "(constrained)". Pin updates now route through the managed-block upsert (higher wins) for all three line types; the rename path keeps in-place coordinate migration, which is how pins and their comments move across a rename
- `fix --apply` (Gradle): Spring DM pins written on a re-run are now credited in the `Applied` report as constrained with their target version — previously a pin-only write (e.g. `net.minidev:json-smart` 2.6.0 → 2.6.1) never appeared in the report at all; an exact no-op (pin already at or above the target) is not credited, so the stall detector stays honest
- The cross-minor-line gate for BOM-managed Gradle artifacts now detects siblings from the resolved classpath instead of only the parsed BOM map: a missing or partial BOM fetch left `bomManaged` empty and over-skipped fixes whose family was in fact aligned. Under Spring dependency management, a qualifying cross-minor fix additionally aligns the whole same-group family to the target line (each sibling gets its own "family alignment" bump) instead of skipping — without a classpath the gate still skips conservatively
- When a pass's approved fixes write no file changes because the manifest already holds every target, `fix` now says so explicitly instead of "No file changes needed (plan already satisfied)" — which previously fed an identical plan signature back into the loop until the stall detector aborted the run
- Cross-major downgrades (`--allow-downgrades`) no longer bypass the co-versioned-family consistency rules that `buildFixPlan` applies to upgrades: a downgrade moving a family member to another major line is refused when the candidate or any classpath sibling is pinned by the project's own `resolutionStrategy.force` on the old line (the pin makes the split permanent), and otherwise every sibling is pulled along to the target line — preferring the primary's exact version when published for that artifact, else the newest safe GA release on the line. Unverifiable sibling release lists or a missing safe target-line release also refuse, keeping the package unfixable with the reason in the report
- `fix --apply` (Gradle) no longer writes managed-block pins that duplicate the project's own `resolutionStrategy.force` lines: user forces outside the managed block are now parsed (including `${var}` references resolved against version defs), a planned pin at the same resolved version is skipped with a warning, and a pin at a different version is written — last force wins in Gradle — but flagged as overriding the project's own force instead of silently replacing it
- The cross-minor-line gate for BOM-managed Gradle artifacts no longer skips fixes whose family has no sibling on the installed release line: any non-downgrade fix crossing a minor line under `enforcedPlatform` was skipped (e.g. `com.google.guava:guava` 33.5.0-jre → 33.7.2-jre) even when nothing shared guava's version line to desynchronize, leaving the CVE unfixable on platforms that manage the vulnerable version indefinitely (every stable Quarkus BOM through 3.39.x manages guava < 33.7.2-jre). The gate now skips only when the platform BOM manages a same-group-family sibling on the installed version's major.minor line (e.g. netty 4.1.x); without a fetched BOM map it still skips conservatively
- Windows Gradle invocation: `windowsBatchArgs` always quoted the executable, but cmd.exe cannot resolve a bare `.bat`/`.cmd` name through PATH when it is quoted, so wrapper invocations failed; the executable is now quoted only when its path contains whitespace
- GitHub Maven advisory fetch: a stale or invalid `GITHUB_TOKEN` / `GH_TOKEN` produced a 401 that aborted supplemental loading; since the endpoint is public, the request now retries once anonymously before failing — and once the token is rejected, every later request in the same run (including pagination) also goes anonymous
- `fix` no longer excludes unfixable coordinates that other resolved packages depend on from all configurations — such a global exclusion removed classes the classpath still loads and broke class loading. The exclude gate now refuses these by default (no prompt, no approval, even under `--apply-excludes`) and reports a health warning naming the dependents; `--force-exclude=group:artifact` overrides per coordinate
- GitHub Maven advisory sync: a bootstrap interrupted mid-pagination (e.g. a rate limit or network failure on page 2) now keeps the pages already fetched as a partial cache and returns them with a warning instead of discarding everything. A cache without its sync cursor counts as incomplete and is re-synced even inside the TTL window, so the next run completes it
- GitHub Maven advisory fetch: an anonymous 403 carrying rate-limit headers now reports `rate limit exceeded (resets <UTC time>)` with advice to set `GITHUB_TOKEN`, instead of a generic HTTP 403 message — and when a configured token was rejected first, the error says so (refresh the token) rather than suggesting to set one
- Downgrade proposals for advisories that list affected versions explicitly: the matcher's exact-version short-circuit dropped the introduced/lastAffected bounds carried by the same block's ranges, so no safe downgrade could ever be computed once the flat `versions[]` list matched (e.g. jackson-coreutils 2.0). The exact path now re-derives the window from the sibling ranges and keeps both bounds
- Downgrade and last-affected promotion for advisories whose affected set is disjoint windows (e.g. json-patch's point list 1.2–1.9, 1.11–1.13): the planner picked the neighboring published release without validating it against the advisory's other windows, so a "fix" could land inside another affected window and ping-pong across passes (1.13 → 1.12 → 1.13). Proposed targets are now checked against every affected block of every advisory naming the package, and the planner walks outward from the installed version until it finds a published GA release escaping all windows — when none exists the package is reported once as unsatisfiable (no published GA version escapes all affected windows) instead of oscillating
- Dry-run and confirm reports listed approved downgrades twice — once in the planned-bumps table (via the effective-approved list) and again in the plan's downgrade section; the render now drops the redundant copy, so each downgrade appears exactly once
- Co-versioned families stuck on an EOL release line can no longer deadlock: when a family's (`jetty`, `netty`, `vertx`, `jackson`) per-artifact fixes are all unpublished on the installed line (e.g. Jetty 11.x went EOL at 11.0.26 while the advisories' minimal fixes point at 11.0.29/11.0.33) or its candidates were clamped/demoted by the family guard, `fix` now attempts a coherent whole-family migration — every classpath member of the family is pinned to the lowest published GA version on the newest installed line or a higher line where no member is affected by any advisory. Lines are tried ascending from the installed one; cross-major migrations respect `--allow-major`, and when no line clears all advisories the per-artifact verdicts are kept with a warning. Members whose coordinate was renamed upstream migrate through the rename instead of a pin (Jetty 12: `org.eclipse.jetty.http2:http2-*` → `jetty-http2-*` and `org.eclipse.jetty:jetty-servlet|servlets|webapp` → `org.eclipse.jetty.ee10:jetty-ee10-*`; successor coordinates live in `KNOWN_RENAMES`), which additionally requires `--allow-renames`, and members with no published version on the chosen line (discontinued or separately-versioned artifacts) stay put and are named in the log. The report gains a Family migrations section, and co-versioned pins appear as `(co-versioned pin)` under Applied. Maven only — Gradle coordinates families through BOMs/platforms
- Maven `dependency:tree` parsing: the indentation after `[INFO]` was stripped before measuring tree depth, so nodes drawn under a last-child branch (space-indented, no leading `|` — e.g. everything under a project's last direct dependency) collapsed into the project root. Parent edges (`requiredBy`) were wrong for exactly those subtrees: WireMock's entire Jetty stack was attributed to the project itself, which misdirected exclusion targeting and hid the top-level consumer from variant-swap detection
- Old-coordinate exclusions after a family migration (Maven) are now attached only to the direct dependencies that actually pull them in, walked up `requiredBy` edges — not every matching `<dependency>` block — and skipped entirely when all sources are being swapped to the migrated variant (nothing left to exclude)
- Human-written comments inside the auto-bumper managed block now survive rewrites: `fix --apply` regenerated the whole block from parsed pins/excludes/forces and silently dropped every free-text comment — including the rationale for why a stack is pinned (e.g. "json-patch 1.13 throws NoSuchMethodError under coreutils 1.12, which is why json-schema-validator stays at 2.2.13"). Comments are now keyed to the entry they document (constraint, force pin, or exclude) and re-emitted next to it; comments above the first entry become the block header and trailing ones the footer, both preserved. A comment whose entry was removed is dropped with it, and on a coordinate rename its comment follows the package to the new coordinate
- Coordinate renames (`fix --apply`) no longer silently drop every `resolutionStrategy { force … }` pin from the managed block: the rename re-render passed an empty force map, so each rename run stripped all forces even when it only touched one constraint. Forces are now parsed, carried through — following their package across the rename — and re-emitted
- Stale `.auto-bumper-bak` backups no longer linger in project roots: at the start of an interactive or `--apply` run, a backup whose content has diverged from the current manifest is deleted (one identical to the manifest is kept — it is still a valid pre-state snapshot, e.g. from an interrupted run). Backup cleanup also runs on every terminal report path instead of only clean exits, so a run that ends with remaining findings no longer leaves the previous run's backup behind
- `fix --apply` no longer reports "bumped via shared variable" when the version def already satisfied the target: the rewrite callback fired (and warned) even when the declared value equaled the requested one, claiming a change the run did not make. The warning now fires only when the def was actually rewritten
- Vulnerability-escape pins are no longer deleted when shadowed by the project's own `resolutionStrategy.force` while that forced version is itself affected: the shadow filter in protection computation stripped the pin unconditionally ("the user's explicit decision wins"), and the managed-block upsert dropped it again without consulting the protection set — so a run on a consumer project removed the entire managed block (the jaxb-core 3.0.2 escape pin plus redundant BOM-stale pins) and left the project's own `force …:4.0.9` line governing, reintroducing CVE-2026-92877. Protection now survives shadowing whenever the user-forced version is affected (last `resolutionStrategy.force` wins in Gradle, and the managed block sits after the project's forces), and only genuinely redundant pins are dropped
- All-digit date-style versions (org.json's `20150729`, `20260719`) were rejected as git hashes by the version-likeness guard (`/^[0-9a-f]{8,}$/` matches pure digits), so advisories whose only fix is a date version (e.g. org.json 20240303 → 20260719) planned no bump target. The guard now rejects a value as a hash only when it contains hex letters. The same class of bad data also corrupted range evaluation: a git-hash `fixed` event in an ECOSYSTEM range overwrote the segment's real fixed bound and hid true positives — such non-version event values are now filtered out of ECOSYSTEM ranges (GIT ranges, which legitimately use commit hashes, are untouched)
- Cross-major downgrades (`--allow-downgrades`) no longer refuse because the project pins the artifact itself: when the project's own `resolutionStrategy.force` pinned an affected version, the family gate treated that self-pin as making a split permanent — but the managed force written after it wins (last-wins in Gradle). The refusal now applies only when the user-forced version is not affected; when it is, the candidate moves alone via its escape pin and the run logs that it overrides the project's own force
- Advisory annotations on existing managed constraint entries no longer vanish on every block re-render: the block parser sliced each line from the regex match length instead of the match end, so an indented `implementation('g:a:v') { because '…' }` line was cut mid-coordinate and the clause was never recognized. Carried-over pins are now re-emitted with their original `because` text
- Version matching for OSV `database_specific.extracted_events` now handles CPE-derived nested items (`{ source, cpe, range: [...] }`) alongside flat event objects. Each nested `range` array is an independent affected window; flat items still form one ordered timeline. Previously the nested shape was read as flat events with no parseable versions, so its windows degenerated to "every version affected": packages whose only matching advisories came from the orphan-CVE bridge (e.g. `log4j-api` at the last fixed 2.x) were falsely flagged and reported unfixable ("no fixed version in OSV") even though every nested window closed below the installed version. Fixed-version and introduced-version collection, and rename-target selection (`maven-renames`, `package-renames`), read the nested shape as well

## [0.0.4] - 2026-10-15

### Added
- `fix --apply-excludes` (Maven/Gradle): unfixable packages (no fixed version in OSV) are excluded from the dependency graph instead of being left reported — Gradle gets a managed `configurations.all { exclude … }` block, Maven attaches `<exclusion>` to the parent dependency. Exclusions are recorded only when every touched project actually wrote them; a Maven direct dependency cannot be excluded and is reported with manual-removal advice instead
- `fix --apply` rewrites the lockfile after a manifest edit so the next scan sees the new pins: `npm install --package-lock-only --ignore-scripts`, `yarn install --ignore-scripts`, `pnpm install --lockfile-only --ignore-scripts`, `bun install --lockfile-only`, `cargo update`, `poetry lock`. `--offline` or a failed refresh leaves the lock unchanged; later scans then trust the lockfile and say so
- Nested manifests below the scan root are included for Maven (`pom.xml`), Gradle (`build.gradle` / `build.gradle.kts`), npm (`package.json`), Cargo (`Cargo.toml`), and Python (`pyproject.toml`, `requirements.txt`). Root files stay parsed by the caller. `node_modules`, `target`, `build`, `dist`, `out`, `vendor`, and VCS/tool dirs are skipped
- Maven candidates with no OSV fixed version but an inclusive last-affected bound are promoted to the next published release after that bound. The last-affected version itself stays vulnerable and is never the target. Skipped when `--offline`
- Fix-loop re-scan overlay now reads Python direct deps (`pyproject.toml`, `requirements.txt`) and npm overrides, so a bumped manifest is visible before the lockfile moves

### Changed
- npm and Python bumps turn ceilings (`<`, `<=`) and a bare `>` into an inclusive floor (`>=`) so the fix version is admitted. Existing floors and exact pins keep their operator

### Fixed
- Direct-parse of Gradle excludes missed single-quoted `exclude group: '…', module: '…'` (the form gradle-editor writes, and idiomatic Groovy), so already-excluded coordinates were re-detected on every fresh session; both quote styles are now collected

## [0.0.1] - 2026-10-14

First release under the new name — rebranded from `@elephantseed/auto-depender`, with version numbering restarting at 0.0.1. Ships everything accumulated in the auto-depender lineage (July–October 2026):

### Added
- Local advisory vendoring for Maven advisories missing from the OSV bulk dump (e.g. vendor-published GHSA entries published after the last dump cut): `local-advisories/Maven.json` is loaded alongside the OSV database and matched by the same engine; ships CVE-2026-102554 (guava, fixed 33.7.2-jre) and CVE-2026-92877 (jaxb-core 4.x line, no fix released yet)
- `fix --latest` (Maven/Gradle): in addition to vulnerability-driven bumps, preemptively bumps every directly declared dependency to the newest non-prerelease available in the project's repositories (falling back to Maven Central). Prereleases and SNAPSHOTS are excluded, qualifier suffixes are preserved (`guava 33.6.0-jre` → `33.7.2-jre`), major bumps remain gated by `--allow-major`, and targets that cannot be resolved from the project repositories are rolled back automatically. Shared Gradle variables and pom properties are rewritten in place, so every dependency using them moves together
- Gradle direct-dep parser resolves version-concatenated declarations (`"group:artifact:" + versionVar`, e.g. `enforcedPlatform("...spring-cloud-dependencies:" + spring_cloud_version)`), so BOM/train imports declared that way are `--latest` candidates like any other direct dependency; unresolvable variables are still skipped
- `fix --apply` re-targets bumps whose target version cannot be resolved from the project repositories (e.g. yanked releases): after Gradle reports a `FAILED` tree node, auto-bumper queries the repository's `maven-metadata.xml` for the smallest available non-SNAPSHOT version above the failed one and bumps to that instead (`~ re-targeted … using X instead`)
- When no such version exists, the bump is rolled back — Gradle restores the exact declared version (downgrade-capable, which a normal bump cannot do) — and the fix is reported under "Skipped — target not resolvable" instead of leaving a broken build
- Manifest overlay on fix-loop re-scan (npm `package.json`, Rust `Cargo.toml` direct deps)
- Clear fix-loop stall messages when `--allow-major` / `--allow-renames` block progress
- `test/manifest-overlay.test.ts`
- Package rename detection for npm, PyPI, and crates.io from OSV advisories
- Manifest renames in `package.json`, `Cargo.toml`, `requirements.txt`, `pyproject.toml`
- Source migrations for JavaScript/TypeScript, Python, and Rust import lines
- Auto source rules derived from applied renames per ecosystem
- `--allow-source-migrations` — generic opt-in for source rewrites after coordinate renames (Java/Jackson today)
- `source-migrations.ts` orchestrator; migration clusters use `source.java` instead of top-level `java`
- Fix report **Planned source migrations** section in dry-run output
- TTY prompt for source migrations (third gate after major/rename)
- `--offline` flag on `scan` and `fix` — skip live OSV API queries; use cached advisory DB only
- Backup restore on `fix` apply failure and uncaught errors (manifests + Java import rewrites)
- GitHub Actions CI (`bun test`)
- `SECURITY.md` vulnerability reporting policy
- Jackson 3 coordinate migration support (`--allow-renames`)
- Opt-in Java import rewrites (`--allow-java-imports`)
- Gradle health warnings for mixed Maven groups and managed constraints

### Changed
- `fix --apply` re-scan cap defaults to 10 (`--max-iterations` to change)
- Rebranded from `@elephantseed/auto-depender` to `@elephantseed/auto-bumper`; version numbering restarts at 0.0.1
- Maven cross-major fixes on unchanged coordinates (e.g. guava `32.1.3-jre` → `33.7.2-jre`) are now planned as major bumps instead of being reported unfixable, and go through the same consent gate as npm (`--allow-major`, TTY prompt, skipped in dry-run/CI). Coordinate renames still take precedence when OSV provides them
- `--allow-java-imports` deprecated (still works as alias with stderr warning)
- Health warnings clarify manifest rename vs source rewrite scope
- README: ecosystem scope table for manifest rename vs source rewrite
- README: Bun required for `npx`/`bunx`, `--offline`, scan vs fix classpath, known limits
- `fix` documents `--allow-java-imports` for opt-in Java import rewrites with coordinate migrations

### Fixed
- `--exclude` packages were filtered only after scan summaries were computed, so excluded findings could still appear in reports; exclusion is now applied before counting and reporting
- Maven projects (Quarkus, Spring Boot) scanning as "No packages scanned" (0 packages): `mvn dependency:tree` ran with `-q`, which suppressed the whole tree (printed at INFO level); the direct-POM fallback then skipped every property-ref / parent-managed version. The tree is now parsed from normal output
- False positives on parallel release lines (Maven backports / LTS branches): a version at or above the fixed version of its own line (e.g. `netty-codec-haproxy` 4.1.138.Final carrying the 4.1-line backport) is no longer flagged just because another range's window numerically contains it; re-introductions (an introduced event above that fix) and explicit `versions` lists still flag
- Missed pgjdbc vulnerabilities (e.g. CVE-2026-107314 / CVE-2026-107315 in `org.postgresql:postgresql`, fixed 42.7.14): OSV publishes them as package-less NVD records, so they are absent from the Maven bulk dump; `pgjdbc/pgjdbc` is now in the default GHSA repo watchlist, so vendor-published advisories with proper Maven bindings are fetched and matched
- `scan`/`fix` invoked from outside the target project now resolve the cache (`.auto-bumper`) against the target project instead of the invocation directory — each working directory kept its own advisory cache, so a run from another folder could serve a stale one and report "No vulnerabilities found" while a scan from inside the project reported findings
- Maven `fix --apply` reported "0 direct, N constrained" for poms that declare versions via properties or literals in later `<dependency>` blocks: the block-matching regex was greedy and swallowed first-to-last `<dependency>`, so only the first block's coordinates were ever inspected — every bump fell back to a `dependencyManagement` pin, which is a silent no-op where the pom declares an explicit `<version>` (the installed version never moved). Dependency blocks are now parsed individually; property-backed bumps rewrite the shared `<properties>` value (max target when several artifacts share one property), literal bumps splice the exact block, and pins remain only for BOM-managed / parent-managed coordinates
- False positives from auto-derived OSV ranges over-covering vendor-backported lines (e.g. `jetty-http` 11.0.29 flagged for CVE-2024-6763 although the 11.x line was fixed in 11.0.27): for GHSA-keyed entries with a non-empty explicit `versions` list, the vendor-curated list is now authoritative and range matching is skipped; CVE-keyed records keep the union of list + ranges
- Maven pins for poms without a `<dependencyManagement>` section were inserted into top-level `<dependencies>`, declaring a real runtime dependency instead of managing a version; a `dependencyManagement` section is now created when missing
- Maven fixes pinning advisory "fixed" versions that do not exist in any project repository (vendor advisories claiming releases that were never published, e.g. `jetty-http` 11.0.29 / `jetty-security` 11.0.31 on the EOL 11.0.x line): each Maven target version is now validated against the repositories' `maven-metadata.xml` before applying, and unpublished targets are skipped (`~ skipped … not published in any project repository`) instead of producing a pom that strict Maven resolvers hard-fail on
- Maven scans silently ignored resolution failures: `mvn dependency:tree` exit status was discarded and lenient wrapper builds report BUILD SUCCESS even with missing POMs, so a bad pin looked resolved and the post-apply rollback (Gradle-only) never fired. Failed runs now extract the unresolvable coordinates ("could not be resolved" / "was not found in" lines) into `ParseResult.unresolved`, enabling the same rollback for Maven
- Missed jackson-coreutils vulnerabilities (CVE-2026-86321 / CVE-2026-86513 / CVE-2026-86511 in `com.github.java-json-tools:jackson-coreutils`): OSV publishes them as package-less NVD records with a GIT range only, and no vendor GHSA exists; the orphan-CVE bridge now covers the product via its repo signal, with curated CVE seeds (`knownCveIds`) for products that have no discoverable security page
- `fix` on Gradle projects scanned runtime classpath only, so test-scoped dependencies (e.g. rest-assured's transitive tree) were invisible to it while `scan` and IDE scanners flagged them; `fix` now scans runtime+test like `scan`
- `--exclude=group:artifact` only prevented bump application — excluded packages were still reported as findings and unfixable, so the tool's own "use --exclude to ignore" hint had no effect; excluded coordinates are now filtered from fix reports and the final verification scan
- `scan`/`fix` status output (⏳ progress, ✅ success lines) went to stderr, which terminals that colorize stderr render red even when nothing is wrong; informational spinner lines now go to stdout and only warnings (⚠️) and errors (❌) stay on stderr
- False positives from GitHub "Duplicate Advisory" mirror records (e.g. `tools.jackson.core:jackson-core` 3.1.7 flagged via GHSA-642r-3gj9-2pj5): mirrors whose affected packages are all bounded by fix data in non-duplicate records are dropped before matching; mirrors without such a boundary are kept (over-report rather than miss)
- Fix report miscount when a bump is applied via a managed constraint block (Gradle/Maven pins): constrained applications are now counted in `Applied N file change(s)` and listed in the `## Applied` table as `(constrained)` instead of being dropped from both
- Scan/fix banner states which Gradle configurations were counted when the scope is restricted (e.g. `fix` scans runtime classpath only, so its package count differs from a plain scan)
- Maven managed-pin block with multiple pins no longer loses all but the first pin on re-render (parser merged adjacent `<dependency>` elements)
- Orphan (package-less) OSV records for bridged products (Log4j) now detected in scans — `mapOsvVulnToAdvisory` enriches with bridged Maven coordinates and the scan pipeline merges the orphan cache
- `--offline` is strict on the DB-load path: a cached dump is used regardless of TTL instead of attempting a download
- Blocked fix-loop message reports source-bound renames (`N rename(s) need --allow-renames; K of them also need --allow-source-migrations`)
- Jackson 3 migration apply policy: old `com.fasterxml` coords excluded, `jackson-bom` removed, no pin for `tools.jackson.core:jackson-annotations`, `jackson-annotations` kept at 2.21
- JS/Python/Rust import editors actually rewrite again (broken backreference + corrupted regex escaping made them silent no-ops)
- Java package rewrites apply longest-prefix-first (`jsr310` → `tools.jackson.databind.ext.javatime`, not the generic rule)
- `fix C:\dev\...` no longer TypeErrors on Windows; prints forward-slash hint for mangled paths
- `--ecosystem=gradle` no longer returns false clean (0 packages) — Gradle tree uses maven coords + `build.gradle` manifest path
- `fix` on Gradle projects now scans with `--ecosystem=gradle` (was `maven`, same false clean)
- Scan/fix exit error when ecosystem filter matches zero packages
- Fix loop: plan-signature stall detection consolidated in `fixLoopStopReason`
- Fix loop: `lastAppliedCount` tracks actual file changes only
- Dedupe applied-bump reporting across loop passes
- `collectFixedVersions` now scopes fix versions to the matching `affected` package block (multi-package advisories)
- Jackson 3 migration keeps `jackson-annotations` 2.x on classpath; no exclude/rename for annotations coord
- Mixed-classpath Gradle projects always keep rename steps in fix plan
- Honest applied-bump reporting for bundled coordinate migrations
- Prefer same-major version bump when OSV lists both patch and major-coordinate fix
